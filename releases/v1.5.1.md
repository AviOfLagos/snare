**A false alarm on incoming code can now be approved.** Found while releasing 1.5.0.

In 1.5.0, when the gate stopped a `git checkout`, a `git pull` or a `git clone`, the code it objected to wasn't on your machine yet. `snare gate allow` only looked at files on disk, so it answered "nothing to allow — clean" while the gate kept blocking. `snare respond` told you to wait for the repo's owner, even when the owner was you. It happened on snare's own repository: the website's demo of the payload is flagged, correctly, as a campaign marker, and nothing could approve it.

### What changed

- **`snare gate allow` looks at incoming code too:** the branch a checkout would bring, the upstream a pull would merge, and anything the gate recorded. Name a branch with `snare gate allow <dir> <branch>`, or approve a blocked clone with `snare gate allow <url>`. An approval is still tied to the file's exact content, so if the file changes it's flagged again.
- **The block prints the exact command to approve it**, for example `snare gate allow /path/to/repo main`.
- **`snare respond`** re-checks incoming blocks, shows each file and line, and offers **allow** or **leave**. If the code really is infected, it points you to `snare fix`.

Branch and pull checks still examine snare's own repository. Skipping them would let a poisoned upstream of snare through unseen. Making a false alarm approvable fixes the dead end without that risk.

### Upgrade

```
snare update
```
