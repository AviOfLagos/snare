  Two routes in
  
Neither one needs you to install anything

  
The same payload shipped two ways. Both execute from an ordinary developer
  action, which is what makes this family effective.

  

    

      
Opening the folder

      
.vscode/tasks.json

      
A task labelled eslint-check,
      marked "hide": true and "reveal": "never", so it never appears
      in the terminal panel. It runs node ./public/fonts/fa-solid-400.woff2.

      
▸ fires on "runOn": "folderOpen"

    

    

      
Starting the dev server

      
postcss.config.js

      
The payload is appended to line 5 after
      thousands of spaces. The file reads as four correct lines of config, because the rest is
      off the right edge of the viewport.

      
▸ fires on next dev / next build

    

  

  

    
The font is not a font

    
A genuine .woff2 begins with the magic bytes wOF2. This file
    begins with 507 spaces, then JavaScript. Disguising the payload as a binary asset keeps it
    out of code review — nobody diffs a font.

  






  Command and control
  
The address lives on a blockchain

  
This is why blocking an IP achieves nothing. There is no hardcoded server —
  the loader derives one, fresh, on every run.

  
    
    
  1. Query public Ethereum RPCsFalls through a list — 1rpc.io, drpc.org, publicnode, blastapi — so no single endpoint can be cut off.
    2. 
    
  2. Read one wallet's outbound transactionsVia the Blockscout API, newest first.
    3. 
    
  3. Take the destination address of the latest oneThe operator controls this by simply sending a transaction.
    4. 
    
  4. Decode two IPv4 addresses out of its bytesThe first eight bytes of the 20-byte address are read as four octets each.
    5. 
    
  5. Fetch stage two and spawn it detachedspawn(..., {detached:true}) then unref() — the process reparents away, surviving the editor that started it.
    6. 
  


  

    
address → two C2 endpoints

    

      

        a322e5f3
        d311d308
        e6f01210
        63e9aDC2
        490Ef1a…
      

      

        bytes 0–3 → primary C2, ports 80 and 443
        bytes 4–7 → secondary C2
        remainder ignored
      

      
Stage two is then pulled from /0x/clb, /0x/cls or
      /0x/ls — XOR-encoded, decoded in memory, eval'd. It never touches disk.
      The observed payload was a clipboard stealer polling every 200 ms.

    

  






  Check by hand
  
Four checks, no tools required

  
Run these against any clone you have. They take about a minute.


  

    
1 · Is a loader running right now?

    
ps -eo pid,args | grep -E "node .*-e .*global\[" | grep -v grep

    
No output means nothing is running.

  


  

    
2 · Does any file carry the operator's wallet?

    
grep -rn "0xa322E5f3D311D3080e6f0121063e9aDC2490Ef1a" .

    
Also check history: git log --all -S "0xa322E5f3" --pickaxe-regex

  


  

    
3 · Is a task set to run when you open the folder?

    
grep -rn "folderOpen" .vscode/tasks.json

    
Any hit here executes the moment the folder opens. Treat as hostile.

  


  

    
4 · Are your fonts actually fonts?

    
head -c 4 public/fonts/*.woff2

    
Every real font prints wOF2. Spaces mean it is a script.

  


  

    
Look for the long line

    
The giveaway is geometry, not content. awk 'length > 1500 {print FILENAME, FNR}' *.js
    finds any config padded out to hide something past the edge of the screen. A hand-written config
    file has no business being 9,000 characters wide.

  






  The tool
  
snare does all of that, everywhere you have code

  
Built while cleaning up this exact infection — four repositories across four
  organisations, which re-infected a freshly reinstalled machine on the next clone.

  

    

      snare guard install
      
Track

      
Watches for the loader and kills it — process and children — within about a second. Only
      ever kills interpreters, so a shell that merely mentions an indicator is left alone.

    

    

      snare scan github
      
Find

      
Checks every repository you can reach through the API without cloning any of them.
      snare scan repo . goes deeper on a clone: working tree, every branch, full history.

    

    

      snare fix owner/repo
      
Fix

      
Backs up to a bundle first, always. Cleans branch tips, or purges the payload from every
      commit in history. Dry run unless you say otherwise.

    

    

      snare notify owner/repo
      
Inform

      
Files a GitHub issue mentioning your collaborators, and opens a pre-filled mail draft per
      person. It never sends anything — you send from your own account.

  Limits
  
What this does not do

  
A guard that oversells itself is worse than no guard.

  

    
It polls once a second, so a payload can act before it is caught. It cannot see code already
    running inside another process, and it will miss variants using different infrastructure.
    Removing the malware from the repository is the actual fix — a running guard is never
    permission to open an untrusted repo.

    
Scanning through the API sees branch tips only. A payload committed and later deleted
    survives in history; use snare scan repo on a clone to catch that.

    
Rewriting history does not touch forks, pull-request refs, or objects still reachable by
    SHA. Ask GitHub Support to garbage-collect after a purge.
